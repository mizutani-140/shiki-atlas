Shiki は、承認済みの **Goal** を「計画 → grill → PRD → Task DAG → 実装 → GitHub 判定 → 修復 → マージ」へと
決定的に進める **エンジニアリング制御面** です。中心的な格言は次のとおりです。

> LLM の出力は揺れてよい。状態遷移は揺れてはならない。

## 自動生成された内部フロー図

下の図は **このページを書いた人が手で描いたものではありません**。
本リポジトリの `.shiki`（Goal・Plan・Task DAG・MergeGate の required checks）を
`tools/generate-shiki-diagram.ts` が読み取り、`npm run build` の前段で Mermaid として生成したものです。

<Mermaid code={diagram} title="Shiki 内部フロー（.shiki 実データから自動生成）" />

CI では生成物を再生成して差分を検査します（`git diff --exit-code`）。
`.shiki` の実状態と図がずれると **ビルドが失敗** するため、図が実データ由来であることが保証されます。

## 図の読み方

- **🎯 Goal / 📄 Plan** — `.shiki/goals`・`.shiki/plans` に登録された実際の Goal と、Spec Freeze 済みの Plan。
- **🧩 Task DAG** — `.shiki/dag` と `.shiki/tasks` から得た実タスク。ランタイム・リスク・必須スキル・受け入れ条件数を表示します。
- **Shiki 内部フロー（スパイン）** — すべての Goal が通る不変の段階：
  Goal Seek → grill-with-docs → Context & Impact → PRD / Spec Freeze → Task DAG →
  Dispatch / Handoff → TDD 実装 → code-review → Pull Request → CCA → MergeGate → Merge。
  CCA が `repair_required` を返すと **Repair Loop** に分岐し、Dispatch に戻ります。
- **MergeGate required checks** — `.shiki/config.yaml` に定義された必須チェック（実データ）。

## なぜ「揺れない状態遷移」なのか

各段階は GitHub Issue / PR / Checks / Reviews と `.shiki` ミラーに**証跡（Ledger）**として残ります。
実装が完了しても、CCA と MergeGate の証跡が揃うまで «完了» とはみなされません。
この図は、その決定的なパイプラインを、まさにこのリポジトリの現在の状態から描いています。
